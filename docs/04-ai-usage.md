# 04 AI 使用说明

## AI 辅助内容

AI 辅助完成需求拆解、LangGraph 状态与动作设计、Python 源码、pytest 测试、合成数据、示例和文档初稿，并根据实际运行修正 Mock 文本长度、Trace 证据与规则摘要。

## 人工要求与修改

用户明确要求必须使用 LangGraph，而不是最初建议的原生循环；每个阶段要细分、完成后汇报并等待确认；所有设计与详细设计都必须写入文件。这些要求形成了 `docs/design/` 的阶段记录和当前工程结构。

用户逐阶段确认了技术选型、方案初设、详细设计、工程骨架与核心 ReAct 链路。

## 验证方式

- Python 编译检查。
- pytest 单元、图和 CLI 测试。
- 五组 Mock CLI 与两组 live CLI 实际运行。
- 对输出与 Trace 做字段级核对。
- 检查最终稿不包含 P01 未支持的“效率提升80%”。

## 模型接入边界

真实模型适配器先按 OpenAI 原生 Responses API 设计；用户随后提供自定义的 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL` 和 `DEEPSEEK_MODEL` 变量名。代码被重构为供应商无关配置，并为 DeepSeek 使用 OpenAI 兼容 Chat Completions JSON 输出。

全量验证实际执行了两条真实模型路径。过程中发现 HTTP 500/522 被错误归类为无效动作，AI 根据 Trace 将传输错误与动作校验错误分离，再次验证后两条路径成功。

离线 Mock 的策略由代码预设。它能验证工具结果确实回到决策接口、不同观察触发不同路径、预算和守卫生效，但不能证明真实模型会作出同样决策。真实 Trace 与 Mock Trace 在评估文档中分开说明。

## 后续修改责任

如果项目作者后续手工修改提示词、规则或算法，应在本文件补充修改及验证结果。若有可用密钥，建议追加至少两条真实模型 Trace，并与 Mock 结果分开说明。

- 通读源码、测试、示例 Trace 与全部文档。

- 复跑正常场景，确认 38.1 秒到 28.0 秒修正一致。
- 复跑工具失败场景，确认退出码为 4。
- 按交付资格、ReAct 证据、场景覆盖、工具风险和文档一致性分级列出问题。

用户特别强调：测试通过不等于提交达标；需要继续核对真实模型证据能否追溯、Trace 参数是否与实际调用一致、验证材料是否覆盖代码中声称支持的失败分支，以及 GitHub URL、题号和 commit SHA 是否真正闭环。

### 用户审计意见与复核结论

以下记录保留用户的审计思路，但不记录任何密钥值或可识别前缀。

1. Git 交付未闭环：确认存在。当前零提交、无远程、无题号、无 SHA。
2. 真实密钥留在 `.env`：确认存在安全风险。文件被忽略，但目录打包、强制添加或聊天暴露仍可能泄漏；该 Key 应作废轮换。原“committed-secret PASS”表述在零提交时不严谨。
3. Mock 决策为预设 if-else：部分成立。Mock 明确只用于流程复现，不计作真实模型能力；已有两条 live Trace，但 live 证据仍需增强可追溯性和动态修正覆盖。
4. Trace 参数与实际工具入参不一致：确认存在。live 搜索动作记录 `top_k`，工具实际读取 `limit`；部分原始决策还包含执行节点忽略的参数。评审视图应记录规范化后的实际入参，并把模型提议参数单独保存。
5. live 记录缺模型追溯信息：确认存在。Trace 只有 `model_mode`，没有 provider、模型名、SDK 版本或响应标识。
6. live 没有超时压缩样本：确认存在。38.1→28.0 仅由 Mock 复现，live 正常路径首稿直接通过。
7. OpenAI Responses 分支无测试：确认存在。现有适配器测试只覆盖 DeepSeek Chat Completions JSON 分支。
8. 工具失败只覆盖检索：确认存在。时长工具、规则工具和执行节点异常兜底没有独立示例与图级测试。
9. 预算上限没有 examples 记录：确认存在。只有单元测试，没有提交输入、输出和 Trace。
10. 缺信息覆盖较窄：部分成立。已有单字段缺失和部分非法值单测，但缺多字段缺失与字段类型错误的正式材料。
11. TIMEOUT 分支无样本：确认存在。枚举和终止映射存在，但没有工具实际返回 timeout。
12. 无依据主张缺 live 拒绝样本：确认存在覆盖缺口。Mock 有数字和非数字检查，live 最终稿已保守化，但没有 live“规则拒绝→模型修订”的证据。
13. 数字主张正则过宽：确认存在。普通步骤数、编号也可能被当作产品效果数字；事实含数字但 `allowed_numbers` 漏登记时会误报。
14. 风险词采用子串匹配：确认存在。可能误伤正常词语，豁免只检查事实原文是否包含相同子串。
15. 产品名过滤要求完全相等：确认存在。简称、别名和轻微变体会被直接过滤。
16. `requested_fields` 不统一：确认存在。Mock 返回机器字段名，live 可返回自然语言描述，下游难以稳定处理。
17. 检测到 Key 和模型即默认 live：确认存在。离线评审漏写 `--model-mode mock` 时可能意外联网。
18. revision 与 Trace 步号边界：确认存在。同指纹稿可降低或保持 revision；决策事件记录调用前步数，观察记录调用后步数，可读性错位。
19. 构建包名和依赖声明：不认定为缺陷。distribution 名 `short-video-script-agent` 与 import 包 `short_video_agent` 不同是 Python 正常做法；`-e .[dev]` 已在全新环境成功解析，且 build-system 声明了 setuptools。egg-info 已被忽略。
20. 工作区 `.venv` 损坏：确认存在。权威验证使用新建 `.validation-venv-20261107`，README 仍需提示不要复用旧环境。
21. 本文档曾写“五次 CLI”：确认存在，已在本次记录中修正为五组 Mock 加两组 live。
22. 阶段文档仍标待确认：确认存在。历史阶段状态尚未统一收口，GitHub 项仍未开始。
23. live 成片明显短于目标：部分成立。当前只实现“不超上限”，形式上满足限制，但 13.2 秒相对 30 秒利用率过低，应增加目标区间或至少风险提示。

### 审计后的人工影响

用户审计使项目从“测试通过即可交付”转为“证据与实现逐项对账”的标准。后续修改必须：

- 不把 Mock 当作真实决策证据。
- Trace 区分模型提议参数和工具实际参数。
- 代码声称支持的关键失败状态要有可执行测试，核心状态要有 examples 记录。
- 真实模型记录应包含不敏感的模型元数据。
- 提交前必须完成 Key 轮换、题号、GitHub URL、commit 和 SHA。

### 批次 1 人工修改与验证

根据用户提出的密钥风险和默认联网风险，人工将配置策略改为“凭据只提供连接配置，不代表联网授权”：未显式设置模式时始终使用 `mock`，仅 `MODEL_MODE=live` 或 `--model-mode live` 可启用真实模型。测试同时覆盖“存在完整 DeepSeek 凭据仍保持 mock”和“显式 live 才启用”两条边界。

原验证快照中的 `committed-secret comparison` 被纠正为 `working-tree secret scan`。原因是当时仓库没有提交对象，无法声称检查了已提交历史。`.env` 虽被 Git 忽略，但忽略规则不能防止强制添加、压缩打包、日志、聊天粘贴或人工复制。已经暴露的密钥必须由用户在供应商后台作废并轮换；代码和测试不能代替该操作。

实际验证结果：隔离环境执行 31 项测试全部通过；额外断言完整凭据但无显式模式时得到 `mock`；Python 编译检查通过；Git 候选工作区秘密扫描通过；`.env` 忽略检查和候选文件排除检查通过。验证过程未读取、打印或调用本地旧密钥，也未发起 live 请求。

### 批次 2—5 人工修改与验证

用户随后要求不再逐项停顿，连续完成剩余整改。人工修改遵循其“实现与证据逐一对账”的验收思路，而不是只增加说明：

- Trace Schema 升级为 2.0，分别保存模型提议参数和执行节点规范化后真正调用工具的参数。未知的 `top_k`、`rule_scope_ids` 等字段只可能出现在提议侧，不能再冒充工具入参。
- 决策事件使用完成后的模型步号并从 1 开始；live 适配器保存 provider、模型名、OpenAI SDK/应用版本和可用 response ID。
- 新增 OpenAI Responses `responses.parse` 离线 stub 测试，与原 DeepSeek Chat Completions 测试共同覆盖两条适配分支。
- 历史 live 文件没有模型名、SDK 版本和响应 ID，迁移时保持空值并标为 `historical_run_metadata_not_captured`，未读取 `.env` 或用当前配置伪造历史证据。
- 增加时长超时、规则工具错误、工具未预期异常、模型步数上限、工具调用上限、多字段缺失和非法字段类型的实际 CLI 输出与 Trace。
- 数字检查排除“第 1 步/2 号”等编号，事实原文数字自动成为允许值；宣传风险词改为短语正则并增加否定/中性表达测试。
- 素材支持显式产品别名；`requested_fields` 改为枚举机器字段，`requested_details` 承载自然语言；重复提交稿件必须严格增加 revision。
- 历史 live 无素材输出的三句自由文本被无损迁移到 `requested_details`，`requested_fields` 规范化为 `product_materials`；动作、工具观察和终止状态未改写。
- 完成稿低于目标时长 70% 时输出偏短风险，不把形式上未超时长的结果错误标成规则失败。
- README 明确旧 `.venv` 已损坏，评审应新建干净环境；历史阶段状态统一收口。

这些变更由新增图级、工具级、适配器级、CLI 和提交示例测试验证。真实模型动态压缩和规则拒绝后的 live 样本仍必须等用户轮换 Key 后再运行；离线 Mock 只能证明流程，不被表述为真实模型决策质量。

最终从此前不存在的 `.validation-final-20261107` 创建干净环境，重新安装依赖后 48 项测试通过，`pip check` 无损坏依赖，`uv lock --check` 通过；全部示例 JSON 可解析，Markdown 相对链接有效，14 份 Trace（12 组离线加 2 组历史 live）均为 Schema 2.0 并含来源元数据字段；候选工作区秘密扫描、`.env` 忽略和候选排除检查均通过。

GitHub 交付检查显示本地仓库仍无提交和 remote，GitHub CLI 的现有账号凭据已失效。AI 没有伪造题号、URL 或 SHA，也没有在缺少认证时假称推送成功；需要用户提供准确题号并重新认证或给出现有仓库 URL 后才能完成最终提交。
